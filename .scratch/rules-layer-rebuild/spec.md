# 规则层重建

## Problem Statement

本仓库的规则散落在 8 个文档、约 615KB 里，并且主要以散文形式存在。散文规则会漂，而且是静默地漂。一次只读审计就查出三条实例：

- 一处状态枚举的取值序与数据库 schema 相反，无任何检查发现
- 一句「某能力尚未装配」散落在 5 个文件 10 余处，无机制保证同步
- 一句声明「数据库列定义以某个迁移文件为准」在新增第二个迁移文件后当场失效，没有一个测试报红

与此同时，本仓库唯一从未腐烂的规则载体是**可执行门禁**：格式化、静态检查、452 条序列化契约用例与真实 MySQL 集成测试。这个反差说明问题不在规则写错了，而在**规则选择了会腐烂的载体**。

对与 AI agent 协作的维护者而言，后果是：agent 读到的规则既冗长又不可信——主规则文件 911 行里只有约 12% 是真正的规范性语句，其余是目录树、模块清单和路线图状态。维护者无法判断哪条是硬要求，agent 也无法执行其中任何一条。

## Solution

把规则层重建为**双层结构**：agent 执行层只承载可执行检查与指向检查的指针，解释性文字一律移入人读层。

核心约束是一条：**任何能被写成断言的规则，不得只以散文形式存在**。散文只保留解释，以及指向对应检查的指针；断言本身放在检查里。机器判不了的规则（依赖方向、归属、意图）留在人读层，并在原地标注「本条无对应检查」，而不是假装它们可验证。

规则分七个类目，各有唯一落点：架构边界与依赖、业务不变量、架构决策、术语边界、验证入口、运行期操作、进度与计划。

迁移采用「先立骨架、后逐条搬迁」：新层目录先立起来，旧文档即刻冻结为只读，此后新规则只能进新层；迁移是同一个提交里删旧加新，中间态不落盘。已存在的规则文件被压缩为纯指针，从 911 行降到 100 行以内。

## User Stories

1. 作为与 AI agent 协作的维护者，我希望每条硬性规则要么是可执行的、要么明确标注了「无对应检查」，以便我知道哪些约束是机器在守、哪些靠人盯
2. 作为维护者，我希望 agent 执行层短到能一眼读完，以便我不必在 900 行里找那条真正重要的约束
3. 作为维护者，我希望规则的「为什么」和「是什么」分开放，以便我既能照做也能理解
4. 作为维护者，我希望新增一条规则的成本是「写断言 + 写一行指针」，而不是「在三个文件里各写一遍散文」，以便规则不再腐烂
5. 作为维护者，我希望任何文档都不能重述数据库 schema 的枚举取值，以便取值变更时文档不需要跟着改
6. 作为维护者，我希望有人把值机的取值抄进文档时门禁能报红，以便这类漂移在发生的当下就被拦住
7. 作为维护者，我希望旧文档被显式标记为冻结，以便任何人（人或 agent）读到它时立刻知道它已过期
8. 作为维护者，我希望迁移是逐条小提交，以便每一步都能评审、出问题能单独回滚
9. 作为维护者，我希望迁移时不会出现「同一条规则暂时存在于新旧两处」，以便迁移过程本身不生产新的漂移
10. 作为维护者，我希望跨越系统的边界决策有单独记录，以便后来者不会把它当 bug 顺手改坏
11. 作为维护者，我希望领域术语有唯一权威定义，以便「实时估价」不会被当成「结算回执」使用
12. 作为维护者，我希望跨文档的链接和锚点都有效，以便点进去不会落空
13. 作为维护者，我希望归档的过程流水不与活跃计划混在一起，以便我不误以为还有事要做
14. 作为维护者，我希望规则文件有单一入口，以便我不需要知道规则散在几个地方
15. 作为首次接触本仓库的新维护者，我希望能在几分钟内知道哪些规则是硬的，以便我快速上手
16. 作为首次接触本仓库的新维护者，我希望历史决策能追溯，以便我不重复当初已被否决的方案
17. 作为首次接触本仓库的新维护者，我希望知道为什么这台机器重复上报刷卡事件不被去重，以便我不把它当缺陷修掉
18. 作为评审者，我希望看到的是一串可评审的小 diff，以便我能对每一步给出有意义的意见
19. 作为评审者，我希望规则变更触及业务不变量时门禁必须跑过真库，以便资金与计量规则有真实证据
20. 作为 AI agent，我希望规则文件里有明确标注「本条无对应检查」的语句，以便我不把散文误当成机器会守的约束
21. 作为 AI agent，我希望执行层每一条都能追溯到一个检查或一句「无对应检查」，以便我照做时不产生虚假的安全感
22. 作为 AI agent，我希望术语定义集中在一处，以便我用词与项目一致
23. 作为团队成员，我希望「能用断言表达的就不该以散文存在」这条规则本身也被机器守住，以便它不会退化成口号
24. 作为团队成员，我希望规则层的结构决策本身有记录，以便我们能理解为什么是双层而不是单层
25. 作为团队成员，我希望归档与活跃文档物理分离，以便搜索时不会命中已完成的批次流水
26. 作为团队成员，我希望新建规则时有一个明确的归类步骤，以便每条规则都有唯一落点而不是随手放进某个文件
27. 作为团队成员，我希望知道哪些规则**无法**断言化，以便不会为了追求 100% 覆盖而产出假信号
28. 作为团队成员，我希望规则层的迁移进度可被追踪，以便知道还剩多少没搬

## Implementation Decisions

- **双层结构**。agent 执行层只允许出现可执行检查与指向检查的指针；解释性文字一律移入人读层。执行层里每一行都必须是可验证的
- **单主缝**。规则层自身的完整性由一个统一的检查入口断言，接入既有门禁编排；不为不同规则分散建检查，避免规则与检查分离
- **该检查断言六条不变量**：
  1. agent 执行层的行数上限（目标 100 行以内）
  2. 执行层中每条规范性语句，要么指向一个存在的检查入口，要么原地标注「本条无对应检查」
  3. 数据库枚举的取值串不得出现在任何文档中，只能是指向迁移 schema 的指针
  4. 所有跨文档引用的文件与锚点均可解析
  5. 冻结文档顶部带冻结声明并指向新层
  6. 架构决策目录编号连续、每份带状态标注
- **第 3 条是最有价值的一条**。它把「顺序有语义的枚举不重述列表」这条维护规则本身变成可执行断言，而这条断言是审计中三处枚举漂移的通用防线
- **检查代码的位置**放在规则检查脚本目录，经门禁编排的子命令调用。与既有数据库脚本的组织方式一致
- **七类目各有唯一落点**：架构边界与依赖（可判定部分转检查，原因进架构决策记录）、业务不变量（多数断言化，解释留在契约文档）、架构决策（独立目录）、术语边界（仓库根的词表）、验证入口（仅指针）、运行期操作（人读）、进度与计划（人读）
- **业务不变量这一类原则上不允许只以散文存在**。凡能写成断言的，散文处只留解释与指针。这是整套设计中最难也最值钱的部分
- **路线图类文档拆解**：其中的架构决策转入决策记录；真正面向未来的部分留作计划；已完成的批次流水归档并移入计划目录下的归档子目录。这两类文档的性质差异很大——前两份共 308KB 记录的是已完成的重构，那是历史而非计划
- **回捞架构决策记录，上限 10–15 条**。已识别的候选包括：部署进程拆分且内部端口两套编排都不映射；后台进程不取微信与支付凭据；真库集成测试单列一层不进默认门禁；白名单常量串不可直接拼进 SQL 的 IN 列表；状态词汇归属领域包而非各用例包。只转满足「难以逆转 + 无上下文时反直觉 + 源于真实权衡」三条齐全的
- **`AGENTS.md` 保留为 agent 执行层**。该文件名是工具约定，指向别处会让约定失效；内容换成纯检查与指针，解释全部迁出人读层
- **迁移策略：先立骨架、后逐条搬迁**。新层目录先立，旧文档即刻冻结为只读，此后新规则只能进新层
- **冻结文档的处理**：迁移是同一个提交里删旧加新，中间态不落盘；冻结声明要显眼，旧文档顶部必须指向新层，让读到它的人或 agent 立刻知道它已过期
- **不使用额外权威源**。迁移对照表会漂，git 历史本身承担追踪职责
- **不承诺 100% 断言化**。依赖方向与意图类约束机器判不了，强行断言会产出假信号，比漂移更危险；这类留在人读层并明确标注
- **已落地的两条架构决策**（本次 grilling 期间写入，供后续遵守）：刷卡重复上报不引入服务端去重，接受设备侧单次报告为上线前的一票否决项；规则层采用双层结构，能用断言表达的一律转成检查而非散文

## Testing Decisions

**什么算好测试**：只断言外部可观察的不变量，不断言实现细节。对本仓库而言，规则层的「外部行为」是门禁对该文档集合的判定结果——哪些规则被机器守住、哪些被标注为人工核对、哪些链接断裂、哪些取值串越界。

**主缝**：一个统一的规则检查入口，六条不变量各一组用例。它复用既有门禁编排，作为默认门禁的一步执行。

**验证外部行为而非实现**：断言「某枚举取值串不得出现在文档中」，而不是「检查脚本里有个叫 xxx 的函数」。文档集合变了断言就该变，检查脚本怎么实现不该被断言绑住。

**既有先例**：本仓库已有成熟的门禁分层——默认检查（格式化、静态检查、单元测试）与真实 MySQL 集成测试分层，后者因需要真实行锁、唯一键与幂等语义而单列。新检查沿用同一思路：能在默认门禁内完成的不引入额外依赖。

**本批不涉及真库**：主缝只读文档与 schema 定义，不需要数据库连接，也不应因为数据库不可用而失效。

**后续批次的缝**：业务不变量的 Go 断言，走既有集成测试约定与真实 MySQL，资金类优先。本批不写。

## Out of Scope

- **不重写业务代码**。除后续批次的断言化所需测试外，不动后端实现
- **不迁移已有规则的内容语义**，只改承载方式与跨文档去重。规则说的是什么保持不变，说法搬家
- **不追求 100% 断言化**。机器判不了的规则留在人读层并标注，这是接受的代价而非待办
- **不做全量决策记录转换**。615KB 里只有满足三条齐全的才转，上限 10–15 条
- **不在本批做业务不变量的 Go 断言**。资金与计量规则的断言化是独立批次
- **不重构既有门禁编排本身**。新检查接入它，不改它的其他行为
- **不动工程技能的配置目录**。它已就位且与规则层正交

## Further Notes

- 本次重建的起点是一次只读三方一致性审计（源码 / 内联注释 / 文档），覆盖约 100 条契约声明，一致率约 85%。**发现高度集中在三类地方**：未接线组件的边界、资金路径的极端分支、文档表格与正文互相矛盾。这个分布本身就是重建的优先依据
- 顺带确认的两个事实支撑了迁移策略：主规则文件 911 行里含「必须 / 禁止 / 不得」的只有 63 行；跨文档重复使「验证入口」「迁移文件名」等概念各自散落在 3–6 个文件
- **最大的执行风险是「能断言表达的就转检查」这条约束的成本**。业务不变量逐条断言化是本批之后最重的工作，尤其资金与计量。规格层面已把它排除在本批之外，但应预期它会成为后续多个批次的主线
- 审计还发现一项已定性但未修复的潜在缺陷：设备计费结算路径存在整数除零风险，发布侧校验可挡住，但结算信任数据库中的冻结快照而不复校验。**这不属于规则层重建范围**，应作为独立缺陷处理
- 重建完成后，规则层的可维护性本身应当可验证：新增一条规则若绕开断言直接写进散文，主缝应当能发现

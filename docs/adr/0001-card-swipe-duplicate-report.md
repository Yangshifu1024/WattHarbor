# 刷卡重复上报不引入服务端去重，接受设备侧单次报告为验收前提

DC589 原生刷卡报文没有事件序号，平台为每帧生成新 UUID，而 `eventKey` 对刷卡事件直接返回该 UUID、不走载荷摘要（同一函数里心跳与故障走的是 sha256 载荷摘要，本可去重）。因此同一张卡**未移开**而被重复报告时，会产生新的去重键、通过去重、并再次扣款。

我们**有意接受**这一行为，不在服务端增加去重。理由：协议没有序号，任何服务端去重都必须区分「合法重刷」与「重复上报」，而两者的唯一区别是卡是否移开过——这个信息只存在于物理世界，服务端拿不到。

本决策在系统尚未上线时作出，此时接受该行为不产生实际资金影响，因此这是一个**有意识的取舍**而非默认遗留。若等到上线后再补做去重，成本更高：既要让新逻辑与既有行为兼容，又要重新验证加时路径。

## 上线前必须解决的条件

设备固件若重复上报一次即产生一次重复扣款，服务端无任何兜底。**「一次放卡只报告一次」因此从流程约定升级为上线前的一票否决项**，验收点见 `docs/operations.md` 的 S6 场景。

若实机验收无法保证该条件，本决策应当被推翻，改为引入设备侧的「卡已移开」信号（属 DC589 协议变更）。

## 被否决的替代方案

- **载荷摘要去重**（与心跳、故障同款）：会把合法的移开重刷一并判为重复，直接破坏加时功能
- **时间窗去重**（N 秒内同卡事件合并）：阈值靠拍，且慢速重刷仍会误伤；把协议缺陷转成一个需要持续调优的经验参数
- **卡片会话指纹**：需要设备侧提供「卡已移开」信号，属于协议变更，超出当前范围

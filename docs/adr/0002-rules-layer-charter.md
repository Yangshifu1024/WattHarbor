# 规则层采用双层结构，能用断言表达的一律转成检查而非散文

规则分两层：**agent 执行层**只允许出现可执行检查和指向检查的指针，不允许出现解释性文字；**人读层**承载完整表述并解释执行层。分类为七类：架构边界与依赖、业务不变量、架构决策（ADR）、术语边界（GLOSSARY）、验证入口、运行期操作、进度与计划。

核心约束：**任何能被写成断言的规则，不得只以散文形式存在**。散文只保留解释与指向检查的指针，断言本身在检查里。

## 理由

散文会漂，而且是静默地漂。本仓库已有实例：`payment_status` 的取值序与 SQL 相反而无任何检查发现；「调度器未装配」一句话散落 5 个文件 10 余处而无机制保证同步；「数据库列定义以 `0001_init.sql` 为准」在某天新增了 `0002` 之后当场失效，没有一个测试报红。相反，`node tasks.mjs check`、452 条序列化契约用例与真实 MySQL 集成测试从未腐烂——它们是本仓库唯一稳定的规则载体。

双层结构是让这条约束可执行的前提：agent 执行层若允许解释文字，规则就总会以散文形态沉淀；把解释赶进人读层后，执行层里剩下的每一行都必须是可验证的。

## 代价

- 许多规则**无法**断言化（如「不得让 worker 复制计费算法」这类依赖方向与意图约束），这类必须留在人读层，并在原地标明「本条无对应检查，靠人工核对」。规则层不可能 100% 断言化
- 业务不变量需要逐条写成断言，这是重建中最昂贵也最有价值的部分——资金与计量规则尤其如此
- 断言会变多，门禁会变慢。取舍是接受更长的门禁时间，换取规则不腐烂

## 不采用的方案

- **全部散文**：本审计已证伪
- **全部可执行**：大量规则机器判不了，强行断言会产出假信号，比漂移更危险

# 业务与接口契约

本文记录当前计量、资金、接口及异步恢复规则。运行入口见 [README](../README.md)，实现与验证边界见 [重构路线图](refactor-roadmap.md)。接口字段以实际路由、DTO 和测试为准。

## 业务规则

### 方案与计量

后台发布完整充电方案，模板应用到站点或设备时复制配置。设备独立配置整体覆盖站点配置。付款意图冻结方案、套餐和费率，订单使用该快照；后续改价不影响历史订单。能力由所选协议统一声明，当前 DC589 支持时长、电量、在线卡、满充停止、累计电量和分段功率，最长 4320 分钟；未知协议不能发布方案或新下单。

| 购买模式 | 算法 | 单位与规则 |
| --- | --- | --- |
| 金额 | `server_max_power` | 电费、服务费为分/小时；按北京时间自然日、费率时段内最高功率档计费 |
| 金额 | `server_realtime_power` | 分/小时；按各实际功率片段所在档计费 |
| 金额 | `server_energy` | 分/kWh；按实测电量计费，跨费率须有边界计量证据 |
| 时长 | 固定时长套餐 | 购买分钟数，按实际完整分钟折算未用金额 |
| 电量 | 固定电量套餐 | 整数 1～65 kWh，售价等于度数乘以电费及服务费单价之和 |

套餐 ID 为 1～99 且唯一，每个启用模式必须配置套餐。用户只能选择服务端生成的套餐。金额模式及刷卡累计保护时长默认 600 分钟，可配置 60～4320 分钟；时长套餐为 1～4320 分钟。损耗系数固定为 0，渠道系数固定为 10000 基点。

金额以整数分保存，费率和中间计算使用十进制。服务器金额模式分别累计电费、服务费后四舍五入到分；设备套餐消耗向下取整到分，分项尾差按既有算法协调。`1 kWh = 1000 Wh`，`1 Wh = 1000 mWh = 3600 W·s`。

DC589 下发配置的刷卡金额 `CardAmountCents` 只能为 0～2500 分且是 10 分整数倍；不能表示的金额直接拒绝，不能截断后下发。上报解码的范围规则保持既有兼容性，协议测试不代替真实设备验收。

完整分钟按整次使用计算，再分配到费率边界；不能逐片段向下取整。最大功率算法只回溯同一天、同一费率时段，不回溯其他时段。免费分钟与最低电费只作用于金额模式：免费范围内或无实际使用不收最低电费，超过免费条件后按完整使用计费。跨费率电量缺少实测边界、计量矛盾或证据不足时进入人工计量复核，不按时间均分或插值补造最终读数。

| 例子 | 结果 |
| --- | --- |
| 实时功率：低档电费/服务费 80/40 分每小时用 20 分钟，高档 120/60 分每小时用 40 分钟 | 电费 107 分、服务费 53 分，共 160 分；付款 300 分退 140 分 |
| 最大功率：同一时段低档升为上述高档，共 60 分钟 | 按高档收 180 分；付款 300 分退 120 分 |
| 300 分购买 120 分钟，实际 61 分 30 秒 | 收 152 分，退 148 分 |
| 电费/服务费 80/20 分每度，购买 3 度，实际 1375 Wh | 电费 109 分、服务费 28 分，共 137 分，退 163 分 |

计算实现和边界示例见 [scheme.go](../backend/internal/domain/charging/scheme.go)。旧兼容计价枚举不表示新方案支持相应模式。

### 支付、启动与结束

扫码发现、端口和套餐查询可匿名访问。下单提交 `client_request_id` UUID、`port_id`、`offer_id`，价格由服务器确定。支付前只保存冻结意图；可信付款回调确认后创建充电订单。相同请求与内容返回原结果，同号不同内容返回冲突。

二维码支持设备码、端口码或带单个 `code` 参数的 HTTPS 链接。裸码为 1～64 位字母、数字、下划线、冒号或连字符；链接禁止用户信息和 fragment。设备码需要继续选择端口，端口码直接定位插口。

微信回调先验签、解密，核对商户、AppID、用户、商户单号、渠道交易号和金额，再同事务写入支付、订单、端口占用及 Outbox。过期付款退款，不启动设备。客户端支付成功不代替渠道回调。

worker 读取持久付款任务，gateway 先保存命令再下发；设备明确回执后推进启动结果。启动超时或回执丢失表示结果未知，保留占用并查询、重试或补偿，不能据此全退或再次启动。设备明确拒绝才按失败处理。

START 回执与 END 事件的失败退避由 gateway 的 `sync_delivery_retry` 按投递身份持久化，worker 经命名内部接口登记固定分类。依赖缺失及临时错误从 1 分钟指数退避，最长 30 分钟；非法内容与未知结果进入核实，每小时重查。首投就绪时间与到期重试时间共同排序，每批最多 50 项，失败不阻止同批独立项。退避不修改回执、冻结结束请求或业务结果；中央确认和网关释放均成功后才标记 END 已处理。补偿受理不表示启动结果已知。

成功标记与对应退避删除同事务；源记录已完成后，迟到失败不能重新建立退避。gateway 在启动时及每小时清理30天前已完成或缺源的历史元数据，每轮最多500条，删除前重查源状态及更新时间。仍未处理的核实／重试项保留，不通过年龄推断设备业务结果。同步批错误返回失败数量及首项单行摘要，保留全部原因的错误链供诊断。

设备结束事件先落库并提交 central；central 保存结束回执、最终计量和计费任务后，gateway 才释放对应占用。首次预算、最长时长、购买时长或用户停止确定计费截止点，迟到的物理停机不增加截止点后的费用。最终实收不超过已付可用额度。后台订单与用户充电快照复用同一实时估价用例，以订单冻结方案和设备观测计算 `live.fee`，仅用于展示；用户端标注“预估费用”与 `≈`，超过 30 秒未更新标记为 stale 并提示旧值。估价不可读取时保留待结算及原因；`total_cents` 等确认金额仍只来自有效结算回执，实时费用不作为最终计费证据。

设备状态全集见 `migrations/*/0001_init.sql` 的 `device_meta.status`（`enabled/disabled/retired/fault`），其中**运营可切换的仅 `enabled/disabled`**，`retired` 与 `fault` 由设备生命周期产生、不经运营开关。启用状态与 TCP 在线状态相互独立。禁用阻止新扫码付款、新刷卡启动及加时，已有订单仍可停止、结算和退款。

自动停止还检测持续至少 1 分钟的端口零功率，最新观测须在 30 秒内；缺失目标端口或重新出现正功率会重置判断。离线、缺失读数不能作为拔出或零功率证据。

零功率证据按入库顺序读取。重复／乱序清空连续时长并保留已接受的最大时间；后续须建立独立完整一分钟窗口。超过 30 秒的相邻间隔同样重置，未来或零时间使当轮判定失败。此恢复规则不缩短预算计量的全历史查询。STOP 受理日志记录来源标签、订单号与命令号；来源标签不代替中央的实时归属授权，也不表示设备已断电。

gateway 在同一设备的操作许可内创建或复用命令、核对占用、保存发送尝试并下发；START／STOP 回执和端口释放共用该许可，网络发送期间不持数据库事务。用户 STOP 只发送给仍由原订单占用的充电端口；启动补偿还允许原订单保留的 idle 占用。释放或换单后的旧 STOP 保留历史但停止派发，不补造设备确认。两类恢复队列在每批 50 条限制之前筛选当前在线设备和原占用，再按最近发送尝试排序；离线历史不会堵住在线任务。该许可属于当前 gateway 进程，不能作为多实例或实机验收证据。

本表只记录各轴的语义。**取值的权威声明一律在迁移 SQL 的列定义里**（MySQL ENUM 按声明序存序位，任何 `ORDER BY` 或序位比较都依赖该顺序），下表不再重述取值串。

| 状态轴 | 语义 | 取值出处 |
| --- | --- | --- |
| `charge_order.status` | 内部生命周期 | `central_db.0001_init.sql` 的 `charge_order.status` |
| `business_status` | 由订单状态派生的 `STORED` 生成列，不直接写入 | 同上 `charge_order.business_status` |
| `payment_status` | 独立支付状态，按实际到账及成功退款更新 | 同上 `charge_order.payment_status` |
| `payment_order.status` | 渠道支付单生命周期 | 同上 `payment_order.status` |
| `refund_record.status` | 退款记录状态 | 同上 `refund_record.status` |
| `refund_record.execution_policy` | **独立于 status**，决定人工审核还是自动执行 | 同上 `refund_record.execution_policy` |
| `payment_intent.status` | 冻结的支付意图，取值词表**不同于** `payment_order.status`，过期付款退款依赖它 | 同上 `charge_payment_intent.status` |

充电结束、费用结算、退款申请与退款到账是不同事实。`processing` 不表示退款成功。

### 在线卡与钱包

卡号为非零 uint32，规范化为十进制字符串。运营人员核实归属后绑定，同一用户可绑定多卡；用户只能挂失或解绑自己的卡。卡使用钱包余额与方案中的时长套餐，不能作为月卡或年卡。

首次刷卡同事务扣钱包、生成支付单和订单、冻结方案、保存卡操作及业务事件记录。充电中同卡重刷沿用原快照，原子追加付款和分钟数，不下发新的 B7。异卡占用、余额不足、启动未确认、已到截止点或整次追加超保护上限时拒绝，不部分扣款。

DC589 原生刷卡报文没有事件序号。gateway 为每次新报文生成 UUID，投递重试复用该 UUID；已完成操作返回原结果，新事件超过 30 秒不再扣款。实机须保证一次放卡只报告一次，移开重刷才产生新事件。设备余额显示使用 0.1 元并向下取整，钱包始终按分记账。

钱包可用金额为 `balance_cents - frozen_cents`，用户档案的 `wallet.available_cents` 使用同一口径，并返回账户状态 `wallet.status`（取值见迁移 SQL 的 `central_db.wallet_account`）。钱包退款按原充值支付单拆分，预留余额及各支付单可退额度。成功才扣减和释放，明确失败释放，渠道结果未知保持预留。5 分钟内第三次钱包退款请求触发频次风控；审核、解冻权限独立，解除一项冻结不自动解除其他冻结。

钱包余额与冻结额必须非负，冻结额不超过余额；流水金额必须为正，余额变动在入账前核对 int64 范围，数据库约束作为最后兜底。各 `created_month` 月键固定为 UTC 月首。微信 OpenID/UnionID 以字节精确比较，有效用户身份、设备编号、端口二维码和设备元数据由独立有效记录唯一键约束，软删除记录保留历史。

实时遥测与补传共用设备行锁和 `(device_id,端口归一键,metric,ts)` 唯一键，采样时间归一到毫秒。原始样本和 15 分钟／小时聚合同事务提交；重放保留首次样本值并跳过聚合累计，插入或聚合失败整体回滚。NULL 端口归一为设备级键 0，业务端口从 1 开始。

### 财务与审核

未用差额按原支付来源返还。累计成功退款与待执行预留共同占用可退额度；渠道超时继续查询同一 `refund_no`，不换号重提。退款成功回执、支付累计已退金额和订单资金状态同事务更新。

微信退款 `PROCESSING/ABNORMAL` 均保持本地 `processing`；`ABNORMAL` 保存渠道退款号和核实原因，继续查原单，不释放钱包预占。只有 `SUCCESS` 确认出账、`CLOSED` 确认失败并释放；迟到异常不能覆盖已确认的终态。异常处理需在商户平台核实，不能通过换退款号或本地标失败释放资金。

人工订单退款限已结束、微信付款且有可退额度的订单。实际启动后已完成或进入退款流程的订单，建单与每次批准均须有 `charge_fee_receipt`，缺回执返回冲突；启动失败、取消或从未启动的订单保留原准入，驳回不要求回执。历史已批准人工单继续查询原渠道退款，查询缺单时才核对费用回执后发起；缺回执保留原退款号等待，已有渠道成功仍按事实入账。人工退款、计量分段修订和发票通过采用不同人员复核；首签冻结业务内容，第二签核对首签人的实时资格及快照。驳回保存理由，重试权限不能绕过人工审核。分段修订保留原总量及冻结来源；缺失计费截止证据不能用物理结束片段替代。人工最终金额结算由有效财务人员按现有权限执行，受实付上限、原因及审计约束。

计费任务 `generation` 随状态转换、人工金额重新排队和计量批准重新排队递增。扫描携带预期代际；失败重排只更新同代际 `pending`，失配直接停止旧执行。人工队列入队和任务转人工在同一个短事务内执行，并重读来源；任务锁不跨计算或资金入账持有。资金入账仍由原费用回执与锁顺序保证幂等。

后台订单详情仅在实时身份有 `order.refund.create` 时返回 `refund_applicant_id`，值为当前管理员的十进制字符串。前端申请草稿按管理员与订单隔离；网络失败沿用同一请求标识，组件卸载或会话变化后的旧响应不得删除草稿或回写界面。接口操作人仍取服务端实时身份。


普通账单由权威计费回执生成；发票申请金额取该回执，同一订单仅允许一份有效申请。导出不提供对账资源；导出使用固定资源白名单生成导出文件（格式取值见迁移 SQL 的 `central_db.export_task.file_format`），限制查询范围、行数和有效期，下载时重新鉴权。账单导出必须传 `filter.from/to`（`YYYY-MM-DD`），最多 31 个自然日，包含首尾日期；后台表单选择完整日期后才提交。

出账有支付关联时，读取失败或关联支付缺失必须返回错误，账单与 `bill_issued` 事件均不生成。调度计数表示费用成功投递，不因出账失败扣减；末尾仍扫描已入账但缺账单的订单，允许同轮补账。`Missing` 不修复历史已写错的账单。

## 接口与权限

普通 JSON 响应为 `code/message/data/request_id/trace_id`，成功 `code=0`，HTTP 状态同时表达结果。`X-Request-ID` 允许 1～128 位字母、数字、下划线或连字符，无效或缺失则生成；响应 trace 与 request 使用同值。微信回调、OpenAPI、文件下载和指标按各自格式响应。

C 端账单 `id`、设备报修提交与列表的 `id` 均为十进制字符串，避免 JavaScript 大整数精度丢失。账单列表和详情返回来源 `order_no`，客户端据此打开订单详情，不将账单主键当作订单号；关联订单缺失时来源不可跳转。钱包流水金额为正数，收支由 `direction` 决定（取值见迁移 SQL 的 `central_db.wallet_txn`）；筛选同样使用 `direction`，业务类别来自 `biz_type`，不得仅按金额符号推断资金方向。

用户端发票、手机号、卡状态和反馈写请求的忙碌状态属于操作及发起会话：隐藏后完成仍释放，返回时尚在途则继续阻止重复提交；确认框也保留打开时的账号。切换账号或卸载后的旧响应不能回写新账号视图或解除新操作。发票未知结果重试复用原请求标识及完整内容，不把后来编辑的内容绑定到旧标识。

金额为整数分，计量字段注明单位。用户 Snowflake ID 使用十进制字符串，前端不得转成 JavaScript `Number`。数据库时间按 UTC 解析，计费日界和 DC589 本地时间按北京时间。列表常用 `page/page_size`，默认 1/20，上限 100；过程查询另有游标、时间窗及行数限制。

用户与管理员使用不同 kind 的 JWT，用户访问令牌有效期 15 分钟，后台访问令牌有效期 8 小时。后台请求前在本地检查到期时间，剩余 30 秒以内时先刷新，并保留 401 后单次刷新重试。身份资料仅在进入会话时同步，登录和续期直接使用响应中的身份及权限。刷新令牌在 Redis 中轮换，后台会话从登录起最长 7 天，续期不延长此期限。用户操作校验 JWT、Redis 会话及有效用户；后台另查 auth_version 和实时角色权限。后台口令使用 bcrypt，可启用 TOTP；后台登录、MFA、刷新按 IP 限速，Redis 不可用时拒绝相关请求。菜单权限只影响展示。服务间接口使用 `X-Service-Token`。

TOTP 校验扫描当前及前后各一步并返回实际命中步骤，碰撞时确定性选最高一步。登录、自助启用／关闭及管理员确认在账号行锁内原子消费时间步，同一密钥的步骤只能递增；新挑战、改密、改角色或强制下线不会恢复旧码。密钥代际独立于 `auth_version`，只有实际更换或清除密钥才重置消费记录。启用后的重新登录须等待验证器切换验证码；挑战消费后的 SQL 失败仍按既有规则重新发起挑战。

登录时正确但已消费或早于已消费步的验证码返回「该验证码已使用，请等待下一个验证码」，不增加账号失败次数、不消费登录挑战、不签发会话；保留已有坏码次数，下一步有效码仍可完成同一挑战。真正错误或过期的验证码累计失败次数，连续5次仍锁定30分钟。HTTP来源限速独立生效，不因正确旧码豁免。

用户匿名入口为 `/scan/resolve`、`/scan/port`、`/scan/offers`、`/station/nearby`、`/station/:id`、`/announcement/list`，均位于 `/api/v1/user`。订单、钱包、卡、手机号和其他用户操作校验当前会话与资源归属。

`/station/nearby` 的经纬度可选：同时提供时按球面距离升序返回半径内的站点，`distance_km` 为计算值，响应 `located` 为 `true`；缺省时按创建时间倒序返回最近创建的站点，默认 10 条，`distance_km` 为 `null`、`located` 为 `false`，客户端须显示为距离未知，不得按 0 公里处理。只提供一个坐标、格式错误或越界仍按 400 处理。

`/station/:id` 除站点资料外返回 `announcements` 与 `devices`。公告包含全部生效的全局公告，以及 `target_ids` 列入本站的站点维度公告；城市维度公告需要用户位置才能判定归属，该接口不做猜测。设备清单来自 `device_meta`，在线状态依据最后心跳时间是否落在 1 小时内判定：从未上报时 `last_heartbeat_at` 为 `null` 且 `online` 为 `false`；gateway 不可达时 `runtime_available` 为 `false`，表示运行态未知，不得当作离线或已测量。

手机号保存在 `central_db.user.phone` 明文列，未绑定为 `NULL`，唯一索引限制号码归属。正式绑定使用微信授权 code，开发模式允许测试号码。绑定响应返回脱敏号码；后台 `user.read` 可读取完整号码并按号码或片段检索，当前没有独立敏感字段权限。后台站点、设备等资源有数据范围约束；订单和支付查询尚无站点或厂商范围过滤。

## Webhook 发送契约（尚未接线）

保留的发送适配器要求目标地址使用 HTTPS，校验 DNS 和目标 IP，拒绝 loopback、私网、元数据地址及 URL 用户信息。签名为 `HMAC-SHA256(secret, timestamp + "." + raw_body)`；`raw_body` 是实际 POST 的报文字节，即**经 `ValidateEvent` 规范化后的完整信封**，因此签名与报文内容始终一致。

| Header | 值 |
| --- | --- |
| `X-ChargePilot-Timestamp` | 十进制 Unix 秒时间戳 |
| `X-ChargePilot-Signature` | `sha256=` 加签名十六进制值 |
| `X-ChargePilot-Event` | 事件的 `object_type`，取值见 `internal/delivery` 的 `Event.ObjectType`（监管事件分类，**不是**订单生命周期状态） |
| `X-ChargePilot-Event-Id` | 稳定事件 ID |

本契约是监管事件投递的契约，与订单、支付、退款等业务事件流不是同一套词汇。发送前会执行 `ValidateEvent` 校验载荷与 `object_key` 一致性，畸形事件不会被投递。

接入时接收方须校验原始请求体签名和时间窗，并按事件 ID 去重。当前 worker 尚未装配此发送适配器，当前消费及游标限制见[异步任务](#异步任务)。

## 异步任务

业务状态与自身 Outbox 同事务提交。Redis 写入成功而数据库发布标记未提交时会重复发布，消费者按稳定事件 ID 和业务回执去重。付款后启动、设备结束、计费和退款以数据库任务为依据，不依赖通知流推进。

| 周期 | 任务 |
| --- | --- |
| worker 每秒 | 告警同步触发、刷卡投递、付款后启动、启动/结束结果同步、Outbox 发布 |
| worker 每 10 秒 | 自动停机、计费、退款派发 |
| worker 调度器每秒扫描 | 当前处理器登记表为空，不执行数据库配置未在代码登记的任务；保留 cron、租约与执行结果机制 |
| gateway 每 5 秒 | 补偿停止，然后用户停止重试 |
| admin 启动及每小时 | 到期导出清理 |

| Stream | 当前用途 |
| --- | --- |
| `charge_payment_confirmed_stream` | 付款确认事件流，启动另读持久任务；当前无 Webhook 消费者 |
| `charge_started_stream` | 明确启动事件流；当前无 Webhook 消费者 |
| `charge_start_rejected_stream` | 明确拒绝事件流，退款另读数据库；当前无 Webhook 消费者 |
| `charge_ended_stream` | 结束事件流，计费另读 `charge_billing_job` |
| `charge_settled_stream` | 最终结算通知，当前无业务消费者 |
| `refund_required_stream` | 退款需求事件流，执行另扫 `refund_record` |
| `refund_succeeded_stream` | 已成功退款事件流；结算由 central `RefundExecutor` 在退款派发行内完成，无独立结果消费者 |
| `refund_result_stream` | 兼容输入，当前无生产者 |
| `wallet_recharge_settled_stream` | 充值通知，当前无消费者，到账已在回调事务完成 |
| `device_event_stream` | 设备事件流；告警同步由 worker 触发、central 经 gateway 内部端点拉取故障记录 |
| `charge_events_stream` | 运维统计清单中的流；当前无注册的后台事件重投处理器 |

当前 worker 将 gateway、user、admin 来源的数据库 Outbox 发布至 Redis；gateway 来源读取 gateway_db，user／admin 来源读取 central_db。Redis 接收成功而 MySQL 发布标记未提交时可重复发布，原 event_id 和业务回执仍用于恢复。当前没有 XRANGE Webhook 外投、订阅管理、通用 DLQ 消费或重放端点；运维 streams 端点只读取配置流的 XLen。DefaultBusinessStreams 是运维统计清单，不建立消费者、外投或重放机制。恢复前须检查实际任务及持久回执，不能据未装配组件推定运行恢复完整。
